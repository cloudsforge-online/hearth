# Coinnomics — the design model, and how it differs from the chain

> ## Read this before any number below
>
> **This document is a MODEL, not the schedule.** Every table here is generated by
> [`../proto/emission.js`](../proto/emission.js), which computes a smooth
> exponential `reward(h) = R0 · 2^(−h/HALFLIFE)` in floating point.
>
> **Consensus does not run that.** It runs a deterministic *integer* schedule with
> linear interpolation inside each two-year epoch
> (`node/src/params.js:140-151`), because floating point in consensus means two
> engines disagreeing by one spark and splitting the chain.
>
> The two differ, and by more than rounding: **the chain issues 11,045,161 EMBER
> in year one; this model says 10,667,873** — about 3.5% apart. §3 puts both
> tables side by side so nobody has to guess which they are looking at.
>
> **For any real number — a listing form, an exchange integration, a supply
> figure, an aggregator submission — use [`tokenomics.md`](tokenomics.md).** It is
> derived from `node/src/params.js` and cited line by line. This file is kept for
> the *design rationale*: why uncapped, why a tail, why 10% to the Commons.

## 1. Units

| Name | Value |
| --- | --- |
| 1 EMBER | base spendable coin |
| ticker | `EMBER` |
| decimals | **18** on the account-model chain (`evm-spec.md` §1) |

The **"spark" (1e-8) is retired with the UTXO chain.** `node/src/params.js:6`
still defines `SPARKS_PER_EMBER = 100_000_000` — the migration to 18 decimals is
specified and not yet implemented ([`decisions.md`](decisions.md) §1.6) — so the
tables below are in whole EMBER, which is unit-independent. Multiply by `1e18`
for wei.

## 2. Time and issuance constants

| Parameter | Value | Why |
| --- | --- | --- |
| Block time | 15 s | fast enough to pay with; big enough to propagate |
| Blocks/year | ~2,103,840 | 365.25 d ÷ 15 s |
| Genesis reward `R0` | 6 EMBER/block | bootstrap security and distribution |
| Reward half-life | 2 years | smooth, predictable disinflation |
| Tail emission `TAIL` | 0.3 EMBER/block (perpetual) | permanent security budget |
| Commons share | 10% of reward | community-funded development |
| Miner share | 90% of reward | pays the people securing the chain |

Those constants are shared by both curves. Emission is halving-free and
continuous either way — the reward falls every single block, with no cliff at an
epoch boundary.

**The design curve** is the smooth exponential

```
reward(height) = max(TAIL, R0 · 2^(−height / HALFLIFE_BLOCKS))
```

**The on-chain rule** is its deterministic integer approximation: the reward halves
each half-life epoch, linearly interpolated within the epoch. It tracks the
exponential closely and is computed bit-identically on any engine
(`node/src/params.js:140-151` ↔ `rust/hearthd/src/ledger.rs`, pinned by a parity
test — `subsidy(4_207_680) == 300_000_000`).

**Linear interpolation is above the exponential everywhere inside an epoch**, which
is the whole source of the 3.5% gap: a straight line between two points on a
convex decaying curve sits above the curve. It is not a bug in either; it is the
price of an integer schedule, and the chain's number is the real one.

Reproduce the consensus column:

```bash
cd node && node -e "
const P=require('./src/params'), S=P.SPARKS_PER_EMBER, BPY=P.BLOCKS_PER_YEAR;
let h=0, total=0n;
for (let y=1; y<=30; y++) {

  total += issued;

    console.log(y, (Number(issued)/S).toFixed(0), (Number(total)/S).toFixed(0));
}"
```

## 4. The fee burn — **withdrawn**

Earlier versions of this document described an EIP-1559-style base fee sized by
congestion and burned, and modelled net inflation approaching ~0% as burn
approached issuance. **That is withdrawn, and `proto/emission.js` still contains
the burn ramp that produced it.** Two facts kill it:

- The UTXO chain's fee is a **flat** 40,000 sparks plus 100 per record byte
  (`node/src/params.js:25-29`) — burned, but not congestion-priced, so it never
  scales with usage the way the model assumed.
- **The account-model chain has no burn at all.** `gasUsed × gasPrice` is paid to
  the block's coinbase, with no burn in v1 (`evm-spec.md` §1). `BASEFEE` exists
  because Shanghai requires it and pushes zero.

**Do not model EMBER as having a burn mechanism. Assume gross issuance equals net
issuance.** Any "net inflation" figure in an older document, including the ~0.37%
at year 30 that this file used to print, is void.

What survives the retraction is the *structural* argument, which never depended on
the burn: emission disinflates into a perpetual tail, so supply growth as a
percentage falls forever without reaching zero — 1.71% at year 10, 1.28% at year
30, and lower forever after.

## 5. Why uncapped, and why that is the point

A hard cap manufactures scarcity, which manufactures hoarding. Money works when
holding it has a small, predictable cost, so it keeps moving. Hearth disinflates
toward a tail instead of stopping: the supply growth *rate* falls every block but
never hits zero.

The tail also fixes the **security cliff**. Chains that plan to pay miners "by fees
alone" have an unproven security budget; a perpetual tail guarantees miners are
always paid, so security never rests on a fee market that has not been
demonstrated to exist.

## 6. Distribution: fair launch

- **No premine.** Genesis holds no spendable balance
  (`node/src/chain.js:55-70`; the one-command verification is in
  [`tokenomics.md`](tokenomics.md) §9).
- **No ICO, no sale, no private round, no airdrop.** You mine or you earn.
- **No founder or VC allocation.** The only "allocation" is the transparent,
  on-chain Commons treasury.

**The caveat:** that genesis is the *UTXO-era* genesis. The account-model chain
gets a new one, and it has not been written. The no-premine property must be
re-verified against its state root when it exists.

## 7. The Commons treasury — and what does not exist

10% of every block subsidy accrues to an on-chain treasury
(`node/src/params.js:22`, enforced at `node/src/chain.js:310-313`). It is intended
to fund core development, security audits, explorers and infrastructure without
selling the network to investors.

**Earlier versions of this document described spending as requiring "an on-chain
proposal to pass hybrid governance" — coin-weighted voting blended with
one-node-one-vote. That is a design sketch with no implementation and it should
not be represented to anyone as a mechanism.**

There is **no spend path of any kind**: no proposal mechanism, no voting contract,
no multisig, no key. Nothing in this repository can move a coin out of the Commons
address. Today it is an accumulator. Under the account model it also needs a `0x…`
address, and one has not been chosen ([`decisions.md`](decisions.md) §2.4).

## 8. Parameter change policy

Consensus constants — block time, `R0`, half-life, tail, commons share — are
intended to be frozen at mainnet. Stability *is* a monetary feature.

This section used to say that `POW_SCRATCH_KIB` 64, `POW_WALK_STEPS` 256 and
`COINBASE_MATURITY` 10 were dev-tuned values that had to be raised to ~2 GiB,
2,048+ and ~100 before mainnet — a hard fork after launch and free before it.
**Two of those three are wrong**, and the correction is measured rather than
argued ([`pow-parameters.md`](pow-parameters.md)):

- **2 GiB is not reachable.** One evaluation at that pad size takes 185.7 s, and
  every node pays a full evaluation to verify every block it receives, against a
  15 s interval. `params.js` now refuses to start above 4 MiB. Making the PoW
  genuinely memory-hard needs an amortised dataset, which is a redesign of the
  PoW across three implementations, not a constant.
- **`COINBASE_MATURITY` is a no-op** on the account model — the subsidy is
  credited straight to the balance and the constant is read only by the retired
  UTXO path.
- **`POW_WALK_STEPS` is genuinely raisable**: 2,048 steps costs 1.31x a 256-step
  evaluation. It is also the parameter that buys the least.

## 9. Stress-test the model

```bash
node proto/emission.js          # prints the MODEL table, and its burn ramp
```

Edit the constants at the top of `proto/emission.js` to explore alternative

the parity test.
